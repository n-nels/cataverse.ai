## 1. Goal
Build a Neo4j graph database that captures:
  (a) the per-experiment procedural sequence (pretreatment steps ->
      experimental conditions -> adsorption parameters), and
  (b) the inter-experiment kinetic chain (AdsParams of experiment X
      conditions the sample state for experiment X+1).
Downstream uses: interactive visualization via Neo4j Aura Free, BO / ML
prediction of AdsParams, and LLM-guided experiment suggestion (mapping
Python functions to physical processes).

## 4. Pipeline (staged; each stage is a separate script presented for review)

### Stage A: `.md` -> `.json`
- For each included `<base>_README.md`, produce a structured
  `<base>_expParams.json` as a PERSISTENT sibling artifact in the same
  folder as the .md.
- All generated JSONs have identical top-level structure (§4.3).
- Do not overwrite an existing `.json` without asking.
- Tuple-valued fields in the .md (e.g.
  `pre_pressure_meas_N = (0.006, 0.0091)` or `(5.238, 'Off')`) are
  problematic downstream [2]. The converter MUST detect these, list
  them, and ask the user before "fixing" them. See §9 for the options.
- Present the script for review before running.

### Stage B: JSON + CSV -> Neo4j artifacts
- Read the JSON metadata + the monomer_sum-filtered CSV rows [3].
- Produce three artifacts under `X:\graphDB\exports\`:
    1. `graph.cypher`          single file, `MERGE`/`CREATE`
                               statements. Paste-or-upload into the
                               Aura Free query editor to populate
                               the database.
    2. `nodes.csv` +
       `relationships.csv`     for `LOAD CSV` / `neo4j-admin import`
                               workflows (alternative ingestion path).
    3. `schema.arrows.json`    schema-only (empty graph, just node and
                               edge types) for import at arrows.app,
                               giving a clean schema diagram.
- Stage B does NOT connect to a running Neo4j instance; it only writes
  files. Connection method is deferred (§9).
- Present the script for review before running.

## 4.1 Graph Schema - Nodes

(:Material)
  - Uniqueness key (MERGE on): metal, metal_loading, support, support_sa
  - Other properties: notebook, mfldVol
  - Expected count: 2. Script must assert this and flag if violated.
  - Example values from the reference README: support = "ceo2" [2].

(:Filename)
  - One per experiment. Uniqueness: base_name.
  - Properties:
      base_name          e.g. "20260428_071207_pd_ceo2_004-017"
      datetime           parsed from the YYYYMMDD_HHMMSS prefix
      exp_type           "adsorption" | "isotopic_exchange" (see §6)
      is_new             Bool  (collapsed from former IsNew node)
      is_reference       Bool  (collapsed from former IsReference node) [2]
      exp_success        Bool  (forced to False when has_csv is False,
                                 regardless of what the README reports --
                                 no CSV means no adsorption data)
      has_csv            Bool  (false when CSV is absent; AdsParams skipped)

(:Pretreatment)
  - One per pretreatment step per experiment. Steps numbered 1..J;
    J varies per experiment. The reference README has multiple steps [2].
  - Properties (prefix 'pre_' dropped; the node label already disambiguates):
      step_index         int, = N
      pre_gas, pre_pressure_meas, pre_pressure_calc,
      pre_temp, pre_rate, pre_duration, pre_chiller

(:ExpConditions)
  - One per experiment. Holds the measurement-step conditions.
  - Properties (prefix 'exp_' dropped; the node label already disambiguates):
      exp_gas, exp_pressure_meas, exp_pressure_calc,
      exp_temp, exp_chiller

(:AdsParams)
  - One per Filename (only when a CSV is present).
  - Selection rule: from the monomer_sum-filtered CSV [3], take the
    single row with the largest `Time (s)`. No delta-window grouping.
  - Properties:
      time_s
      pfo_sec_r2, pfo_sec_rmse,
      pfo_sec_k_a,   pfo_sec_k_a_stderr,
      pfo_sec_q_e,   pfo_sec_q_e_stderr,
      pfo_sec_k_s,   pfo_sec_k_s_stderr,
      pfo_sec_k_p,   pfo_sec_k_p_stderr,
      pfo_sec_q_inf, pfo_sec_q_inf_stderr,
      pfo_sec_q0

**new**
--------------------------------------------------------------------------
(:AdsParams)
  - One per (Filename, peak_name).
  - Selection rule: from the CSV [3], group rows by `Peak_Name`, then
    within each peak_name take the single row with the largest
    `Time (s)`. No delta-window grouping.
  - For v1, only `Peak_Name == 'monomer_sum'` rows are loaded, so
    every AdsParams node has peak_name='monomer_sum'. The schema is
    forward-compatible: future expansion to `cluster_sum`, `Peak_1975`,
    `Peak_2093`, etc. requires only relaxing the load-time filter. No
    schema migration needed at that point.
  - Properties:
      peak_name          str, e.g. "monomer_sum"
      time_s             the Time (s) of the selected row
      pfo_sec_r2, pfo_sec_rmse,
      pfo_sec_k_a,   pfo_sec_k_a_stderr,
      pfo_sec_q_e,   pfo_sec_q_e_stderr,
      pfo_sec_k_s,   pfo_sec_k_s_stderr,
      pfo_sec_k_p,   pfo_sec_k_p_stderr,
      pfo_sec_q_inf, pfo_sec_q_inf_stderr,
      pfo_sec_q0
----------------------------------------------------------------------

(:KineticChain)
  - One per unbroken chain of experiments on a physical sample.
  - Properties:
      chain_id           stable hash of (material_key, started_at)
      material_key       for traversal convenience
      started_at         datetime of first experiment in the chain
      length             int, count of experiments in the chain
      mass_g             catalyst mass in grams. Sourced from each
                         experiment's material.mass_g in the JSON;
                         constant within a chain. Stage B hard-stops
                         if experiments in the same chain disagree.

## 4.2 Graph Schema - Edges

Static / per-experiment structure:
  (Material)        -[:HAS_EXPERIMENT]->      (Filename)
  (Filename)        -[:CONDUCTED_UNDER]->     (ExpConditions)
  (Filename)        -[:HAS_STEP {order:N}]->  (Pretreatment {step_index:N})
  (Pretreatment N)  -[:NEXT_STEP]->           (Pretreatment N+1)
  (Pretreatment J)  -[:NEXT_STEP]->           (ExpConditions)
  (ExpConditions)   -[:YIELDS]->              (AdsParams)

Kinetic (inter-experiment) chain:
  (Filename)        -[:IN_CHAIN]->            (KineticChain)
  (Filename X)      -[:NEXT_EXP]->            (Filename X+1)
    -- :NEXT_EXP edges exist ONLY between experiments in the same chain.

Plain-English notes on the edges (for humans reading this spec):

  * `(Filename)-[:HAS_STEP {order:N}]->(Pretreatment {step_index:N})`
    reads as "the Filename node has an edge labelled HAS_STEP (carrying
    a property `order` = N) pointing to a Pretreatment node whose
    `step_index` is N." The `N` is NOT a single max value. It is a
    template instantiated once per step. An experiment with 4
    pretreatments produces 4 separate HAS_STEP edges from that one
    Filename [2]. The edge property `order` and the node property
    `step_index` are intentionally redundant so the edge is
    self-describing on its own.

  * Why both `:HAS_STEP {order:N}` and `:NEXT_STEP`?
    - `:HAS_STEP {order:N}` answers "give me step N of experiment X
      directly" in one hop, no traversal.
    - `:NEXT_STEP` answers "walk through the procedure in order" using
      Cypher's natural chain traversal syntax.
    Keeping both costs a handful of extra edges per experiment and
    makes both query styles trivial. Dropping either one is fine if you
    decide you only ever use the other.

## 5. Kinetic Chain Logic
A KineticChain is a maximal time-ordered sequence of experiments on a
single physical sample with no reset.

Build algorithm:
  1. Collect all in-scope Filenames across all 6 subfolders.
  2. Sort by `datetime` parsed from the filename prefix
     (YYYYMMDD_HHMMSS) [2].
  3. Walk the sorted list; start a NEW KineticChain whenever:
        - `is_new == True` for that Filename.
     Otherwise, append the Filename to the current chain and add
     (prev_Filename)-[:NEXT_EXP]->(this_Filename).
  4. After the walk, set KineticChain.length and started_at.

Notes:
  - A change in Material implies `is_new == True` (can't swap material
    without a physical reset), so the Material-change case is already
    covered by the is_new rule. For these samples specifically, a
    Material change is also captured by a change in `pd_loading`
    (part of the Material uniqueness key in §4.1), so no separate
    Material-change branch is needed in the chain-break logic.
  - READMEs without a matching CSV (§3) still participate in the chain.
    They appear as Filename nodes with `has_csv = false` and no
    AdsParams, but they still consume / alter sample history and so they
    still break or extend the chain.

Semantics reminder:
  - is_new = True  -> fresh sample physically loaded into the cell
                      (same material OR different material) -> NEW chain.
  - is_new = False -> continuing on the sample already in the cell.

## 6. exp_type Inference
- Default: `exp_type = "adsorption"`.
- If the base filename contains `iso` (case-insensitive):
  `exp_type = "isotopic_exchange"`.
- Per §3, iso-tagged experiments are excluded from this build. The
  rule is kept here for forward compatibility and so the `.md -> .json`
  converter still tags them correctly if/when they are re-included.

## 7. Missing-Value Policy and Review List
- Do NOT guess values. Ever.
- Maintain `X:\graphDB\review\missing_values_review.txt` as a plain
  text file. One record per missing field, one per line, in this shape:

      <base_name> | <field_name> | <node_label> | <notes>

  Example:

      20260505_063850_pd_ceo2_004-018 | is_new_sample | Filename | absent in README
      20260428_071207_pd_ceo2_004-017 | ceo2_sa       | Material | absent in README

- Known suspect field: `is_new_sample` may be missing in some READMEs.
- Any Filename with one or more missing required fields still gets a
  node, BUT the missing property is written as `null` (not invented)
  and the field is recorded in the review list.
- EXCEPTIONS to the "flag in review" rule (write null silently, do NOT
  record in the review file):
    * `chiller` on any Pretreatment or ExpConditions. This field was
      added late to the data schema and is legitimately absent from
      older READMEs.
    * All ExpConditions fields when `has_csv == False`. No CSV means
      the experiment never ran, so the ExpConditions block was never
      populated by design.
    * Empty pretreatments list (J=0) when `has_csv == False`. This is
      a "sample present, no experiment conducted" record -- legitimate
      state. Stage B creates the :Filename and :Material nodes and
      includes the experiment in its :KineticChain, but omits the
      :Pretreatment, :ExpConditions, and :AdsParams nodes/edges.
      J=0 with `has_csv == True` IS still flagged; that combination
      indicates an experiment that ran without recorded pretreatments
      and requires human review.
  These exceptions apply in both regular runs and --dry-run.
- Stage B MUST NOT silently coerce `null` booleans into `false`. In
  particular, `is_new == null` must NOT be treated as `is_new == False`
  for the chain-break rule in §5. If `is_new` is null, STOP and ask
  the user.
- The review list is for manual human review. Regenerate it on every
  Stage A / Stage B dry run; do not append blindly.

## 9. Open Items - Ask User Before Coding

### 9a. [x] Tuple-valued fields in the .md
The reference README contains fields whose value is a Python-style
tuple, e.g. `pre_pressure_meas_3 = (5.238, 'Off')` and other measured
pressures like `(0.006, 0.0091)` [2]. These break downstream typing.
The converter must flag every tuple-valued field it encounters and ask
which option to apply (same answer applied uniformly, unless the user
says otherwise):

  (a) Keep as a two-element array, full fidelity.
      Downstream code must handle mixed-type elements (float + string
      like 'Off').
  (b) Keep only the first element (the actual measurement). Discard
      the second (uncertainty, status flag, or sentinel).
  (c) Split into two properties: `<field>` (first element) and
      `<field>_aux` (second element). Preserves information and keeps
      each property single-typed.

Recommended default (pending user confirmation): (c).
RESOLVED: Two flat properties `pressure_meas_g1` / `pressure_meas_g2`
(distinct gauges). String 'Off' -> null. Supersedes option (c).

### 9b. [x] Neo4j connection method (deferred)
Stage B writes files only; it does not connect to a live Neo4j
instance. When the user is ready to load into Aura Free, pick one of:

  (a) Paste `exports/graph.cypher` into the Aura query editor manually.
  (b) Use Aura's CSV import with `exports/nodes.csv` +
      `exports/relationships.csv`.
  (c) Add a small loader that connects over Bolt using credentials in
      environment variables (`NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`).

Recommended default (pending user confirmation): (a) for the first
load, because it is the most reviewable. Revisit (c) once the pipeline
is stable.
RESOLVED: (b) CSV import. `exports/nodes.csv` + `exports/relationships.csv`
are the primary deliverables; `graph.cypher` kept as backup/audit.

## 10. Caveat: Drafted Without Direct Access
These instructions were drafted WITHOUT the LLM having direct access
to the working directories (`X:\peakFit\` and `X:\graphDB\`). Paths,
file counts, field names, and example values are based on what the
user described and on a single reference README [2] and CSV [3].

If during implementation you (Claude Code) find ANY of the following,
STOP and flag the user rather than silently reconciling:

  - `X:\peakFit\` does not contain 7 subfolders, or the `_test` folder
    is named differently, or there are additional exclusions that
    should apply.
  - A README field name in the actual files differs from §4.1 / §4.3
    (e.g. `is_new_sample` vs `is_new`, `pre_pressure_meas_1` vs a
    different key).
  - The CSV column names, ordering, or the `Peak_Name == 'monomer_sum'`
    convention differ from §4.1 AdsParams.
  - The assumed YYYYMMDD_HHMMSS datetime prefix does not parse cleanly
    for some filenames.
  - More than 2 distinct Material keys emerge under the §4.1
    uniqueness definition.
  - A README has no pretreatment_N sections (J=0) AND has a matching
    `*_CarbonylPeakArea.csv` sibling. J=0 + no-CSV is handled per §7
    EXCEPTIONS; J=0 + CSV present is a data bug requiring review.
  - Any other structural surprise not covered above.

In all such cases: do not guess, do not "fix," do not proceed. Report
the discrepancy, propose options, and wait for the user.
